## A. Что это

Реляционная база **отклонений** производства (импланты/абатменты, инструмент — свёрла и т.п.).
Airtable QMS — начальный фрагмент, не проект целиком. Принцип: Claude — «голова»
(архитектура/спеки/анализ), не «руки»; ничего не строим, пока модель не разобрана
и план не утверждён.

## B. Устойчивое ядро (согласовано во всех трёх сессиях)

### Item (центральная сущность)
Производимая деталь (item number). Центр модели: основная масса группировок, сортировок,
запросов — по нему.
- Обязательные справочники (администрируемые, ведёт админ): **Item type**, **Connection type**
  (C1, V3, IntHex, LYNX, **General — default**), **Size** (NP, SP, WP, **General — default**).
- **CG-привязка** — необязательна, связь **many-to-many** «на вырост» (на практике сейчас 0..1).
- «Item с 0 CG» — **массовый случай**. Item с 0 характеристик не возникает (в базу попадает
  при первом Deviation, а тот всегда привязан к размерам).
- 2 скрытых поля Airtable — rollup для отчётов, **не переносим**.

### Характеристика (размер)
**Атрибут Item, НЕ самостоятельная сущность.**
- Ключ **(деталь + локальный №)**; номер уникален только внутри детали.
- «Размер 12» в отрыве от детали не существует; «размер 12 детали XXX» и «…YYY» — разные
  характеристики, совпадение номеров — случайность.
- Связь характеристик разных деталей — только через канон (маппинг), никогда через номер.
- В реляционной модели ляжет в отдельную таблицу (нормализация «многие к одному»).
- При создании Item заводятся только CG-размеры; прочие — по факту поступления Deviation
  (не-CG размер при первом Deviation **автоматически** привязывается к Item, форма не нужна).

### CharacteristicGroup (CG) — канонический слой
- Малый **статический справочник** (≈20–30 на систему). Заводит **админ** (отдельный процесс —
  снимает «курицу-яйцо», не часть потока Item).
- Имя (напр. `Implant_Con_375_C1`), набор канонических позиций **g1…gN**.
- Номинал/допуск **зашиты в схему CG** (с чертежа); модератор их не вводит.
- Версионирования на этапе 1 нет. CG 2-го уровня (связь конструктивно похожих деталей) — не сейчас
  (влияет лишь требованием держать Item↔CG как m:n).

### Маппинг (cross-table)
- Связь **(деталь, локальный №) → каноническая g-позиция**.
- Строится **вручную, инкрементально**; назначает человек при заведении; готовой кросс-таблицы нет.
- **Необязателен**: размеры вне CG (массовый случай) живут без канона.
- Код **99** = «позиции у детали нет» (техническая заглушка; на практике пока не встречалась).
  Не поисковый ключ; пара `g:99` явно фиксирует «позицию рассмотрели, её нет».

### Deviation (отклонение) — самостоятельная сущность
- **decisionDev** — живой, не процедурный, на уровне Deviation, не наследуется, не выводится авто.
  **Словарь из 4 значений (s05)** — см. «Исходы Deviation» ниже.
- **explanation** — текст, всегда; ведётся вручную; → документ **אישור חריגה только при одобрении**;
  решения не несёт (может словами ссылаться на инспекцию). Это **не** то же самое, что процедурное
  поле бланка с типом Inspection (s05): оба сосуществуют — свободная ссылка словами и структурная подстановка.
- **Attachment** — ссылки на документы (фото, отчёты измериловки) в открытой сетевой папке; уровень Deviation.
- Атрибуты: Item, WO, machine (опц.), quantity, date, **NCR** (s05), **decision_date** (s05).
  Находки 1..N; Inspection 0..N.
- **NCR (s05)** — строковый атрибут, заполняется вручную; номер может прийти **позже** решения
  (на момент внесения его может не быть). Открывается с привязкой к WO, но группируется по типу проблем:
  разнотипные отклонения → разные NCR; однотипные внутри WO → один общий номер. Технически несколько
  Deviation просто несут одну строку — отдельная таблица не нужна, поиск «все отклонения по NCR» работает.
  Если Deviation разнороден по типам — номер вешается на любую из проблем; тип NCR присваивает QA
  в своей системе по наиболее существенной для них проблеме, к нашей модели отношения не имеет.
- **decision_date (s05)** — поле с дефолтом по системному времени (документ может печататься позже решения).
- Целостность — на уровне Deviation: расщепить по размерам нельзя (потеряется картина детали).

### Три уровня количества (s05 — зафиксировано явно)
1. **WO / מנה** — весь товар, выпущенный под этим номером на машине. `פק"ע` и `מנה` — **синонимы**,
   официальное название `פק"ע` (Work Order). Отдельного уровня «партия» над WO в модели нет.
2. **Deviation** — количество деталей на одно отклонение (`quantity`); парсится из таблицы-источника.
3. **Находки** — размеры внутри одного отклонения; **своего количества не несут**.

> [!warning] Глоссарий проекта (`terminology`) описывает `מנה` как «отмеренное количество, **не весь наряд**» —
> это расходится с определением пользователя (s05: синоним WO). Помечено для согласования, не правлено.

### Исходы Deviation (s05) — словарь `decisionDev`

| Code | Label (EN) | Что происходит с деталями | Закрывающий документ |
|---|---|---|---|
| `approved` | Approved — use as is | Идут дальше по процессу без изменений | **DS-QC.2-2** `אישור חריגה` — этап 1, основной и самый частый |
| `rejected` | Not approved — scrap | В брак | **нет документа** |
| `sorting` | Sorting — 100 % screening | 100 % сортировка по заявленному критерию (допуск может быть расширен относительно базового); годные идут дальше | Общий бланк sorting/repair, режим *sorting* |
| `repair` | Repair | Ремонт до приемлемого, но **не полностью соответствующего** состояния: отклонение остаётся, но санкционировано | Тот же бланк, режим *repair* |

- Термин **`repair`**, не `rework` (решение пользователя s05): деталь не возвращается в полное
  соответствие чертежу.
- `decisionInsp` остаётся **бинарным** (`approved` / `not approved`) и от `decisionDev` независим:
  инспекция отвечает «можно ли принять это отклонение», а не «что делать с партией».
- **Бланки sorting/repair в модели не поддерживаются** (s05): в ~95 % случаев заполняются вручную,
  данные под них не хранятся; критерий сортировки в модель **не заводится**.

> [!important] **Граница области (s05).** Как только решение внесено, дальнейшая судьба деталей —
> вне этой базы. Сортировка → QC → годные на склад, негодные в брак; ремонт → проверка → при
> необходимости повторный ремонт или сортировка. Повторный возврат возможен, но это уровень
> **комитета по отклонениям** (зависит от процента брака в WO) — отдельная тема, здесь не моделируется.

### Находка (Finding) — отклонение по одному размеру внутри Deviation
- Адресуема для поиска; **решения НЕ несёт**.
- Поля: `dimension_main` (по нему привязка к канону), `dimension_point` (индекс точки, опц., в поиске
  не участвует), `direction` ±, `value` (опц.), `comment` (сырой текст для качественных/нераспознанного),
  **Affected zone** и **Deviation type** (справочники на находке, для глубокого поиска).

### Inspection (исследование) — детализировано в s04
- **Отдельная сущность/таблица.** Строка заводится ТОЛЬКО когда выполнена серьёзная,
  документированная, переиспользуемая проверка влияния отклонения (есть письменное summary).
  Рутинная первичная проверка (`Tolerances review` — сверка по чертежу, включая беглый визуальный
  осмотр посадки деталей в SolidWorks) порождает находку и записи inspection НЕ заводит.
  Критерий — не инструмент, а наличие письменного переиспользуемого анализа.
- **Привязка к находке** (Вариант B, ратифицировано s04); **0..N** на Deviation. Смысл: работает
  симметричный поиск «все inspections по (Item, размер)» — зеркало «все deviations по (Item, размер)»;
  разные размеры одного отклонения могут нести разные исследования. Отвергнут Вариант A (к Deviation
  целиком, 0..1): исключал бы поиск инспекций по размеру. Единица выдачи поиска всё равно Deviation
  целиком (см. «Сквозные принципы»).
- **decisionInsp** независим от decisionDev; копит информацию, **не диктует** решение (задача базы —
  дать исчерпывающий объём информации, не решать за инженера).
- **Поля (минимум):** `Inspection ID`; `Тип` — из администрируемого словаря (старт: `Solidworks assembly`,
  `Implantation torque test`; на вырост: `Drilling force test`, функциональная проверка); ссылка на находку;
  `Inspection Result` (decisionInsp) = `Deviation approved` / `Deviation not approved`; `Protocol` — приложенный
  документ (summary). `Item` выводится из Deviation/находки, отдельно не хранится.
- **Вся «наука» — в протоколе, не в полях:** метод, статистика (T-test, p), прибор + калибровка, состав
  выборки, worst-case модификации, «вторая деталь» (партнёр по сборке / медиум измерения), картинки
  with/without deviation. Согласуется со «Сквозными принципами» (кросс-связки деталей — текстом).
- **Примеры (из прежней БД):** `Implantation torque test` — момент введения импланта при отклонении
  сверла (dim 19, +); `Solidworks assembly` — worst-case зазор в сборке (CS-TB015A dim 32 −, партнёр
  C1-08375A), вывод approved.

### Сквозные принципы
- **Решения живые, не процедурные** (инженер смотрит сопутствующее — напр. чистоту поверхности:
  сломанный инструмент → задиры → reject, хотя числа в норме).
- **Кросс-связки размеров** («AA одобряется, если BB в норме») — НЕ структура данных, только текст
  в explanation/inspection.
- Поиск по (Item + размер) матчит по находке, но **единица выдачи — всегда Deviation целиком**.

## C. Процесс и вход

### Источник данных
Excel в Teams, иврит/RTL, прямого доступа нет (только через Valerii/копию). Столбец מידה (размер) —
рудимент, не заполняется. Якорь (размер, величина, направление) — **в свободном ивритском тексте** описания.
Отлов: оператор каждые 2 ч проверяет деталь; при отклонении отделяются все детали с последней успешной
проверки; после WO — выборочная проверка, дефект в выборке → весь WO в MRB. Знак: **− ниже минимума,
+ выше максимума**.

### ETL (этап 1)
Автопарсинг регулярками → корректировка → **утверждение оператором** (модерация).
- Костяк: `מידה {N} חורגת {מעל המקסימום=+ | מתחת למינימום=−} {עד|ב} {value}`; пин: `מידה {N} פין {v} נכנס/לא נכנס`.
- **Направление — из max/min-слова (приоритет)**; знак числа — вторичная проверка/флаг конфликта.
- Много грязи (опечатки מינמום/נינימום, знак приклеен/отсутствует, дубли слов).
- `X מתוך Y` (выборка) → **quantity = 9999**; под-индекс точки — голое число (`12 1`).
- `מדיד`/`GO` — качественные (величины нет); пин — измеримый, но на этапе 1 в comment.
- 1 строка Excel → 1 Deviation с массивом находок; этап 1 — ручная загрузка по одной.

### Поиск
- **Ось канона:** находка → g-позиция → отклонения других деталей по той же позиции (точно, для CG-размеров).
- **Ось zone/type:** находка → Affected zone + Deviation type (сквозная, для всех находок).
- **Глубокий поиск = конструктор запросов** (этап 1.5, только чтение): любое поле трёх уровней
  Item↔находка↔Deviation↔Inspection как ось; логика не ограничена (AND/OR, диапазоны, вложенность).
- Справочники Affected zone / Deviation type: пополняет **оператор** (при вводе), чистит **админ**;
  отдельная таблица. Zone и CG раздельны: zone — мягкий поисковый ярлык; CG — строгий канон с геометрией.

### Выходной документ — `אישור חריגה` (разобран в s05)

**Бланк:** `טופס תיעוד קבלת החלטה בעקבות אישור חריג למנה` · MIS Forms · QA&RA / Quality Control ·
**DS-QC.2-2, מהדורה 2.0, תחולה 2024/12/16**. Образец разобран на реальном экземпляре (WO W26007336,
Item MT-SRH19A, 2 Deviation).

- **Выпускается только при `approved`.** Галочка `לא קביל` в бланке — рудимент, в практике
  не используется; для брака документ не заполняется вовсе.
- **Один документ — на WO/מנה целиком**, внутри перечисляются несколько Deviation, у каждого —
  своё `כמות שאושרה` и своё описание. Исключение: отдельный инцидент, который нужно одобрить
  до попадания партии на QC, — документ выпускается на него.
- **Этап 1 — заполняется вручную.** Автогенерация и триггер вне области этапа 1. Требование к базе
  переформулировано: нести все поля так, чтобы заполнение бланка было копированием из карточки.
