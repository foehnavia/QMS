## 1. Центральная сущность — Item

**Item (item number)** — производимая деталь/компонент. Это центральный узел модели: основная масса группировок, сортировок и запросов идёт по нему.

Item обладает:
- набором **характеристик** (размеры: номинал + допуски);
- **состояниями** (стадии: до/после электрополировки, закалки и т.д.), от которых характеристики могут зависеть;
- характеристики могут входить в **общие группы**, переиспользуемые между деталями (например, implant connection zone — общая для семейства имплантов; drill shank — общая для свёрел и части инструмента).

---

## 2. Характеристика (размер)

**Характеристика — это атрибут (свойство) Item, а НЕ самостоятельная бизнес-сущность.**

Ключевые свойства и ограничения:
- Характеристика **полностью зависит от Item**: нет детали — нет её характеристик (identifying-связь).
- Идентифицируется парой **(деталь + локальный номер)**, не номером в одиночку.
- **Локальный номер уникален только в пределах детали.** Каждый номер имеет одно и только одно значение.
- «Размер 12» сам по себе не существует. Существует только **«размер 12 детали XXX»**.
- «Размер 12 детали XXX» и «размер 12 детали YYY» — **абсолютно разные характеристики**. Совпадение номеров между деталями — случайность, не связь.
- Несмотря на то, что характеристика концептуально — свойство детали, в реляционной модели она ляжет в отдельную таблицу (строка = «характеристика такой-то детали»), т.к. их много и на них ссылаются. Это нормализация «многие характеристики у одной детали», а не повышение характеристики до уровня сущности.

Единственное, что **по-настоящему связывает** характеристики разных деталей, — привязка к одной **канонической характеристике** (через маппинг). Через номер — никогда.

---

## 3. Канонический слой (общий референс)

Назначение: общий референс нужен **как ключ для анализа и группировки отклонений**, и при этом он же хранит значения/допуски (см. §5). Не для «шаринга номеров» — номера у деталей разные.

Рабочие имена (обсуждаемые):

- **CharacteristicGroup** — каноническая группа: «implant connection zone семейства X», «drill shank». Одна на семейство/класс; на неё ссылаются детали.
- **Каноническая характеристика** — позиция (слот) внутри группы. Например, у connection zone их три. Это якорь группировки: по нему собираются отклонения сквозь все детали и состояния.

Пример: имплант XXX (размеры 12, 14, 16) и YYY (размеры 18, 22, 36) имеют идентичную зону implant connection с тремя размерами. Номера разные, но это аналитически одни и те же три канонические позиции.

---

## 4. Состояния (State)

Состояние — **полноценное измерение представления характеристики, а не флажок на замере.**

Обоснование (пример drill shank у детали ZZZ):
- размер **№8** до электрополировки = **1.95 мм**;
- после электрополировки превращается в размер **№44** со значением **1.94 мм**.

То есть при смене стадии у характеристики меняются и **номер**, и **значение**. Поэтому:
- №8 и №44 в ZZZ — **разные характеристики одной детали**, связанные только через общий канон drill shank;
- значения по состояниям: {до ЭП: 1.95}, {после ЭП: 1.94} — общие для всех свёрел семейства.

> Состояния обсуждены частично (на примере). Остаются вопросы, которые проговариваем в следующей сессии.

---

## 5. Где хранятся значения и допуски (решение по Q1 — закрыто)

**Значения и допуски живут на паре (каноническая характеристика, состояние), а не у детали.**

Доводы:
- **Один источник истины.** В семействе значение позиции одно; хранение у каждой детали = дублирование и риск рассинхрона при правке спеки.
- **Соответствует реальности.** Значение — свойство характеристики (+состояние), а не детали. Деталь несёт лишь локальный номер-ярлык.
- **Чистый анализ.** Отклонение резолвится в каноническую позицию → сразу есть номинал/допуск для сравнения; тот же запрос ловит отклонения других деталей по той же позиции.
- **Состояние ложится естественно** — значения по стадиям в одном месте, без дублирования.

Механизм единообразия: у характеристики **всегда ≥1 состояние**; «бесстадийные» имеют ровно одно — чтобы в коде не было двух разных путей.

### Исключения — выводим, а не закладываем
- По логике исключений быть не может: в пределах семейства значения и допуски идентичны по конструкции.
- Возможны редкие отклонения из-за ошибки/аврального внесения изменений.
- **Решение:** НЕ строить override-слой ради подстраховки. Цель программы — максимально ускорить и упростить работу; максимальная группировка ценнее, чем пара выпадающих деталей.
- **Механизм вывода** точечный, на уровне **отдельного размера**: для проблемного размера просто **не делаем привязку** к канонической характеристике (маппинг пустой). Деталь остаётся в группе по остальным размерам и выпадает только по проблемному.

---

## 6. Маппинг (cross-table)

- Связь **(деталь, локальный номер) → (каноническая характеристика, состояние)**. Значения не несёт, только связь.
- Примеры: №8 → (drill shank, до ЭП); №44 → (drill shank, после ЭП).
- Кросс-таблицы совместимости готовой нет — **строим инкрементально, вручную**, по мере поступления отклонений.
- Привязку назначает **человек при заведении** (авто-резолва нет); база копится со временем.
- Цикл при пустой базе: получили отклонение → вносим Item → определяем наличие групп характеристик → если группа ещё не определена, вносим и размечаем → привязываем нужный размер к разметке так, чтобы, например, поиск по размеру 12 детали XXX выдавал и отклонения детали YYY по размеру 18.
- **Привязка необязательна** (см. §5 про исключения).

---

## 7. Отклонение (Deviation)

- **Самостоятельная сущность**, НЕ часть Item.
- Ссылается на **конкретную характеристику конкретной детали** = (деталь + локальный номер), всегда внутри детали. Это его **обязательная опора**.
- С Item связано **только через характеристику**, напрямую — нет.
- До канонической характеристики добирается **через маппинг, если он есть**.
- **Нет маппинга → отклонение валидно и видно по самой детали, просто не попадает в каноническую группировку.** Это нормальный ожидаемый случай, не ошибка данных.
- «Отклонения по размеру 12» в отрыве от детали — невалидный запрос. Валидно: «по XXX-12» или «по канонической позиции, в которую XXX-12 входит».

Диагностическая цепочка резолва:

    Deviation → (Item, локальный №) → Mapping → Каноническая характеристика (+ State)

Это **надстройка** над обязательным базовым слоем (Item + характеристика + отклонение), а не обязательная его часть. Базовый слой работает всегда; каноническая группировка — поверх, для привязанных размеров.

## 9. Сводка сущностей (промежуточная, НЕ финал)

| Сущность | Что это | Ключевое |
|---|---|---|
| Item | Производимая деталь/компонент | Центральный узел; локальные характеристики |
| Характеристика (размер) | Атрибут Item | Зависит от Item; ключ (деталь + локальный №); номер локален |
| CharacteristicGroup | Каноническая группа | Общий референс на семейство (connection zone, drill shank) |
| Каноническая характеристика | Слот внутри группы | Якорь группировки; хранит значения/допуски по состояниям |
| State | Стадия (до/после ЭП, закалка) | Меняет номер И значение характеристики |
| Mapping | (деталь, лок. №) → (канон. характеристика, состояние) | Ручной, инкрементальный, необязательный |
| Deviation | Отклонение | Отдельная сущность; опора на (деталь+№); канон через маппинг |

> Имена рабочие. Диаграмму модели единой картинкой собираем **после** того, как будет передана оставшаяся информация и закрыты открытые вопросы.
