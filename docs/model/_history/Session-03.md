## 1. Item (центральная сущность)

**Item (item number)** — производимая деталь/компонент. Центральный узел: основная масса группировок, сортировок и запросов идёт по нему.

### Форма создания Item (закрыта в с03)
- **Item number**
- **Item type** — обяз.; справочник (Implant, Healing Cap, Pilot Drill, Drill, Ti-Base, Blank, Connect abutment, Multi-Unit, Insert, Drill Stopper, EZ-Base, Scan Post, Analog, Screw … — администрируемый).
- **Connection type** — обяз.; справочник (C1, V3, IntHex, LYNX, **General — default**).
- **Size** — обяз.; справочник (NP, SP, WP, **General — default**).
- **CG-привязка** — необяз.; связь **many-to-many** (на практике сейчас 0..1).
- Обязательны все, кроме CG. По заполнении Item сохраняется и готов к использованию.
- Справочники type/connection/size — **администрируемые** (ведёт админ; оператор не пополняет).
- 2 скрытых поля из Airtable — это **rollup** для отчётов, **не переносим** (вопрос закрыт).

### Жизненный цикл размеров (характеристик) Item
- При создании Item заводятся **только CG-размеры** (через форму привязки к канону).
- Прочие размеры — **не заранее**: появляются по мере поступления Deviation по ним. Размер вне CG при первом Deviation **автоматически** привязывается к Item (форма не нужна).
- «Item с 0 CG» — **массовый случай** (большинство деталей). Наличие CG — меньшинство.
- Item с 0 характеристик не возникает: Item попадает в базу при внесении Deviation, а Deviation всегда привязан к размерам.

## 2. Характеристика (размер)

**Атрибут Item, НЕ самостоятельная сущность.** (детально — с01/с02)
- Зависит от Item (identifying); ключ **(деталь + локальный номер)**; номер локален и уникален только внутри детали.
- «Размер 12 детали XXX» и «размер 12 детали YYY» — разные характеристики; совпадение номеров — случайность.
- Связь характеристик разных деталей — только через канон (маппинг), никогда через номер.

---

## 3. Канонический слой и CharacteristicGroup (детально, с03)

### CG — что это
- Малый **статический справочник** (≈20–30 на систему). Создаётся **администратором** (с Claude/Claude Code) — базовый функционал UI, **отдельный процесс**, не часть потока Item. Снимает «курицу-яйцо».
- Имя (напр. `Implant_Con_375_C1`), набор **канонических позиций g1…gN** (N — своё у каждой CG; 11 — только пример).
- Номинал/допуск **зашиты** в схему CG (с чертежа), модератор их **не вводит**.

### Состояния (State) на уровне CG
- **Смена состояния ВСЕГДА влечёт смену номера размера** (жёсткий инвариант; пример сверла: размеры 3/15 до ЭП → 24/23 после).
- Состояния разнесены как **отдельные g-баллоны** (баллон у размера + баллон у сноски состояния). Привязка строго **1 баллон = 1 локальный размер = 1 привязка**. Никаких составных «до/после» внутри пары.

### Версионирование CG
- На первом этапе **нет** (скорее всего не будет вовсе). При изменении конструкции — новая схема + cross-reference старая↔новая, но это редкость («вырос толеранс») и не сейчас.

### CG 2-го уровня — НЕ сейчас
- В будущем появятся CG, связывающие **конструктивно похожие** (не идентичные) детали. Отдельный пласт. На первый этап влияет лишь требованием держать связь Item↔CG как **many-to-many** «на вырост».

## 4. Форма привязки детали к CG (с03)

- Интерактивная схема CG (визуальный редактор маппинга): отрисовка с g-номерами (g1…gN) — чтобы не путать с локальными номерами Item.
- Каждый **баллон кликабелен** → поле ввода **локального номера** размера заводимой детали → баллон становится ярко-зелёным.
- **Заполнение всех баллонов обязательно.** «Сохранить» активна, когда все заполнены.
- **Код отсутствия — 99**: означает «у детали этой позиции нет». На практике **деталей с 99 пока не встречалось** — чисто техническая заглушка на будущее.
- По «Сохранить» пишутся пары **(деталь, локальный №) → g-позиция** в маппинг; CG становится доступной в ячейке CG формы Add Item.
- Семантика `99`: зарезервированный код «позиции нет», **не поисковый размерный ключ**. Резолв item→канон на `99` не выходит (отклонений с размером 99 нет); канон→item по g с `99` просто не даёт реального номера (деталь по позиции не входит в выдачу). Пара `g:99` явно фиксирует «позицию рассмотрели, её нет» — чище, чем отсутствие пары.

---

## 5. Маппинг (cross-table)

- Связь **(деталь, локальный номер) → каноническая g-позиция**. (состояние «зашито» в то, какая это g-позиция — см. §3.)
- Готовой кросс-таблицы нет — строим **инкрементально, вручную**; назначает человек при заведении.
- **Привязка необязательна.** Размеры вне CG (массовый случай) живут без канона.

## 6. Рабочий процесс: импорт отклонения (с03)

### Вход
Строка Excel (иврит, RTL) парсится. **Поля Deviation:** WO, machine (опц.), Item number, quantity, date, **массив находок**. (Item number адресует/создаёт Item; остальное — наполнение Deviation.)

### Парсинг находок (структура)
Якорь (размер, величина, направление) живёт **в свободном ивритском тексте** описания (структурного поля нет, столбец מידה мёртв).
- **Метод (этап 1):** автопарсинг → проверка/корректировка → **утверждение оператором** (модерация).
- Текст полуструктурирован, костяк регулярен: `מידה {N} חורגת {מעל המקסימום=+ | מתחת למינימום=−} {עד|ב} {value}`; пин: `מידה {N} פין {v} נכנס/לא נכנס`.
- В данных много грязи (опечатки מינמום/נינימום, знак то приклеен, то отсутствует, дубли слов). **Направление — из max/min-слова (приоритет)**; знак числа — вторичная проверка/флаг конфликта.

### Структура находки (минимальная, этап 1)
- `dimension_main` — основной номер. **Поиск и привязка к канону — по нему.**
- `dimension_point` — индекс точки (повторное измерение размера в неск. точках), опц.; **голое число без `מתוך`**; в поиске не участвует.
- `direction` — +/−, опц. (нет у калибра/Go-No-Go).
- `value` — величина, опц. Есть у числовых и у **пина** (вычисляется из границ — но вычисление отложено на этап 2, пока ручная модерация). **Нет у калибра/Go-No-Go**.
- `comment` — сырой текст для качественных (пин, מדיד, GO, визуал) и нераспознанного.
- **Affected zone** — справочник, **на находке**, для глубокого поиска.
- **Deviation type** — справочник, **на находке**, для глубокого поиска.

### Конвенции парсинга
- `X מתוך Y` (выборка) → **quantity = 9999**. `{N} מתוך {M}` после размера = это **количество**, не индекс точки.
- Под-индекс точки — голое число (`12 1`, `12 3`).
- `מדיד`/`GO` — качественные (величины нет); **пин** — даёт величину (измеримый), но на этапе 1 в comment.
- `מידה מידה 24` и пр. — опечатки, чистятся.

### НЕ первый этап (явно отложено)
- **Типы измерения с привязкой к размеру + квалитет точности** (их много; влияют на расчёты) — большой пласт, этап 2+.
- **Вычисление value из пинов** — этап 2 (пока ручная модерация).
- **Контекст обнаружения** (במהלך המדגם / מיון 100% / planned) — **не работаем вообще**.
- **הערה יצרן** (примечание изготовителя) — **не обрабатываем**; в реальности это поле для уточняющих вопросов инжиниринга и промежуточных рекомендаций, к первичной обработке не относится.

### Гранулярность / загрузка
- 1 строка Excel → **1 Deviation** с массивом находок.
- Этап 1 — **ручная загрузка, 1 Deviation за раз**. Автоматизация (вкл. дедуп ежедневной выгрузки) — позже.

## 7. Логика привязки входа к существующим сущностям (с03)

Первое, что делает система — пытается привязать вход к существующему:
1. Есть ли **Item** в базе?
2. Есть ли внутри него нужные размеры?
- Размеры подтягиваются/создаются по факту: не-CG размер, которого нет, при Deviation **автоматически** привязывается к Item (форма не нужна).
- Форма создания Item нужна, когда **нет самого Item**. Тогда же разово заводятся CG-размеры (через форму привязки, §4). Предусловие: если у Item есть CG — она **уже должна существовать** в справочнике (заведена админом заранее).

## 8. Deviation — сводка (с02 + уточнения с03)

- Самостоятельная сущность. **decisionDev** (живой, не процедурный, на уровне Deviation, не наследуется).
- **explanation** — текст, всегда; → документ **אישור חריגה только при одобрении**; decision не несёт; вручную.
- **Attachment** — ссылки на документы (фото, отчёты измериловки) в открытой сетевой папке; **уровень Deviation**.
- **находки 1..N**; **Inspection 0..N** (привязка к находке, Вариант B).
- Атрибуты: Item, WO, machine (опц.), quantity, date.
- Affected zone / Deviation type — **на находке** (не на Deviation).
- Кросс-связки размеров — НЕ в модели (текст в explanation/inspection).

---

## 9. Поиск (с03)

### Две оси
- **По канону:** находка с привязанным размером → g-позиция → отклонения других деталей по той же позиции. Точный, для CG-размеров.
- **По zone/type:** находка → Affected zone + Deviation type. Сквозная смысловая ось; **для всех находок** (особенно не-CG, где канона нет; CG 2-го уровня — не скоро).

### Справочники Affected zone / Deviation type
- Администрирование **иначе, чем у Item**: пополняет **оператор** (при вводе), чистит **админ**; **отдельная таблица** для удобства модерации.
- Affected zone и CG — **раздельны**: zone — мягкий поисковый ярлык на находке; CG — строгий канонический справочник с геометрией. Оба обслуживают поиск с разных сторон.

### Глубокий поиск = конструктор запросов (этап 1.5)
- Фактически **конструктор запросов**: **любое поле** трёх уровней (Item ↔ находка ↔ Deviation ↔ Inspection) — потенциальная ось; **логика не ограничена** (AND/OR, диапазоны, вложенность).
- Пример: «все deviations с Item type=Implant, Connection=C1, Size=SP, Affected zone=outer thread, Deviation type=thread pitch» — соединяет атрибуты Item и находки; выдача — на уровне **Deviation**.
- Требование к модели: поисковые поля — **нормализованные типизированные колонки/справочники** (ровно ради этого данные вытаскиваются из ивритского текста). Структура с01–с03 под это готова.
- **Приоритет — этап 1.5**: сразу после отладки основной структуры. На 1.5 — **только чтение**. Далее — экспорт в документы и «…до бесконечности».

## 10. Inspection — намечено (детальный разбор — следующая сессия)

- Сущность; **decisionInsp** независим от decisionDev (две независимые характеристики).
- Привязка **к находке** (Вариант B); **0..N** на Deviation.
- Копит информацию, **не диктует** decisionDev. Решения живые, не процедурные (с02 §9).
- Задача базы — **дать исчерпывающий объём информации**, не решать за инженера.
- Две формы-близнецы: «все deviations по (Item, размер)» и «все inspections по (Item, размер)».

## 11. Этапность (с03)

- **Этап 1** — рабочая структура базы: ручной ввод с модерацией, Item / находки / Deviation / CG / маппинг в полностью рабочем состоянии.
- **Этап 1.5** — глубокий поиск (конструктор запросов), **только чтение**. Высокий приоритет, сразу после каркаса.
- **Дальше** — экспорт результатов в документы (אישור חריגה и др.) и наращивание «…до бесконечности».

## 12. Открытые вопросы / на следующую сессию

- **Замкнуть поток Deviation:** что физически происходит при сохранении (как находки ложатся, привязка к размерам Item, когда идёт резолв в канон).
- **Inspection** — детальный разбор сущности (что несёт кроме decisionInsp; research vs inspection; практика привязки к находке).
- **Итоговая документация** — אישור חריגה и др. (структура, триггер генерации, что тянется из базы).
- **WO** — финальное решение атрибут/сущность (с02 §10, отложено).
- Типы измерения + квалитеты; вычисление value из пинов; дедуп автозагрузки — этап 2+.

## 13. Сводка сущностей (промежуточная, НЕ финал)

| Explanation | Текст-обоснование | Всегда; в אישור חריגה; decision НЕ несёт |
| Affected zone / Deviation type | Справочники находки | Поиск; оператор пополняет, админ чистит; отдельная таблица |
| WO | Рабочий наряд | Пока атрибут Deviation; кандидат в сущности (отложено) |
