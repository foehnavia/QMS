## 1. Центральная сущность — Item

**Item (item number)** — производимая деталь/компонент. Центральный узел: основная масса группировок, сортировок и запросов идёт по нему.

Item обладает:
- набором **характеристик** (размеры: номинал + допуски);
- **состояниями** (стадии: до/после электрополировки, закалки и т.д.), от которых характеристики могут зависеть;
- характеристики могут входить в **общие группы**, переиспользуемые между деталями (implant connection zone — общая для семейства имплантов; drill shank — общая для свёрел и части инструмента).

---

## 2. Характеристика (размер)

**Характеристика — атрибут (свойство) Item, НЕ самостоятельная бизнес-сущность.**

- Полностью зависит от Item: нет детали — нет её характеристик (identifying-связь).
- Идентифицируется парой **(деталь + локальный номер)**, не номером в одиночку.
- **Локальный номер уникален только в пределах детали.** Каждый номер имеет одно и только одно значение.
- «Размер 12» сам по себе не существует. Существует только **«размер 12 детали XXX»**.
- «Размер 12 детали XXX» и «размер 12 детали YYY» — **абсолютно разные характеристики**. Совпадение номеров — случайность, не связь.
- В реляционной модели ляжет в отдельную таблицу (строка = «характеристика такой-то детали») — это нормализация «многие к одному», не повышение до сущности.

Единственное, что связывает характеристики разных деталей, — привязка к одной **канонической характеристике** через маппинг. Через номер — никогда.

---

## 3. Канонический слой (общий референс)

Назначение: ключ для анализа и группировки отклонений; хранит значения/допуски (см. §5).

- **CharacteristicGroup** — каноническая группа: «implant connection zone семейства X», «drill shank». Одна на семейство/класс.
- **Каноническая характеристика** — позиция (слот) внутри группы (у connection zone их три). Якорь группировки сквозь все детали и состояния.

Пример: XXX (размеры 12, 14, 16) и YYY (18, 22, 36) имеют идентичную connection zone из трёх размеров. Номера разные — позиции аналитически одни и те же.

---

## 4. Состояния (State)

Состояние — **полноценное измерение представления характеристики, а не флажок на замере.**

Пример (drill shank, деталь ZZZ):
- размер **№8** до электрополировки = **1.95 мм**;
- после ЭП превращается в размер **№44** со значением **1.94 мм**.

При смене стадии меняются и **номер**, и **значение**. Поэтому №8 и №44 в ZZZ — разные характеристики одной детали, связанные только через общий канон drill shank.

> Состояния обсуждены частично (на примере). Детальный разбор — на будущей сессии.

---

## 5. Где хранятся значения и допуски (решение по Q1 — закрыто)

**Значения и допуски живут на паре (каноническая характеристика, состояние), а не у детали.**

Доводы: один источник истины (нет дублирования/рассинхрона); значение — свойство характеристики+состояния, а не детали; чистый анализ (отклонение резолвится в каноническую позицию → сразу есть номинал/допуск); состояние ложится естественно.

Единообразие: у характеристики **всегда ≥1 состояние**; «бесстадийные» имеют ровно одно.

### Исключения — выводим, а не закладываем
- По логике исключений нет (в семействе значения идентичны по конструкции); редкие — из-за ошибки/аврала.
- НЕ строим override-слой. Цель — ускорить и упростить; максимальная группировка ценнее пары выпадающих деталей.
- Механизм вывода точечный, на уровне **отдельного размера**: для проблемного размера не делаем привязку к канону (маппинг пустой). Деталь остаётся в группе по остальным размерам.

---

## 6. Маппинг (cross-table)

- Связь **(деталь, локальный номер) → (каноническая характеристика, состояние)**. Значения не несёт.
- Примеры: №8 → (drill shank, до ЭП); №44 → (drill shank, после ЭП).
- Готовой кросс-таблицы нет — **строим инкрементально, вручную**, по мере поступления отклонений.
- Привязку назначает **человек при заведении**; база копится со временем.
- **Привязка необязательна** (см. §5).

## 7. Источник данных (новое, сессия 02)

Откуда приходят отклонения сейчас:

- **Excel-файл в Teams** с открытым, но ограниченным группой доступом. Прямого доступа к рабочему файлу нет (политика безопасности) — только через Valerii или выгружаемую копию.
- Файл на **иврите, RTL**. Прочитанные столбцы (справа налево): אחראי (ответственный), פק"ע (**WO / рабочий наряд**), מכונה (станок: G5/G9/...), מק"ט (**item number**), כמות (количество), תיאור חריגה (описание отклонения, свободный текст), מידה (размер — **задумывался для фильтрации, НЕ заполняется, рудимент**), הערה יצרן (примечание изготовителя), תאריך שליחת חריגה (дата отправки), עדיפות (приоритет), החלטת משרד טכני (решение тех. отдела: מאושרת/לא מאושרת), תאריך סגירה (дата закрытия), הערה (примечание).

### Как работает отлов отклонений (процесс)
- Каждые **2 часа** оператор проверяет последнюю вышедшую из станка деталь.
- Нашли отклонение → **все детали с момента последней успешной проверки** отделяются; описываются все отклонения по всем размерам; фиксируется количество отделённых.
- После завершения WO — **выборочная проверка** деталей, дошедших как годные. Нашли дефект в выборке → **весь WO помечается MRB**.
- Каждая строка Excel = либо «партия, остановленная оператором» (с количеством отделённых), либо «итог выборочной проверки» (количество пустое или число дефектных из выборки). Смысл כמות **зависит от типа строки** («N מתוך M» в выборочных).

### Важные наблюдения из источника
- Якорь **(Item, локальный №)** и величина/направление выхода за допуск живут **внутри ивритского текста** описания (структурного поля нет → между источником и моделью нужен слой извлечения/изменения процесса ввода — флаг на будущее).
- Знаковая конвенция: **− ниже минимума, + выше максимума**.
- Находки **неоднородны**: числовые (выход на величину) и **качественные** (калибр-пин «заходит/не заходит», чистота поверхности).
- Одна строка может перечислять отклонения **по нескольким размерам**.

## 8. Deviation (отклонение) — проработано (сессия 02)

**Deviation — однозначно самостоятельная сущность.** НЕ часть Item. Привязана к Item и к WO.

### Структура
- **decisionDev** — ключевая характеристика. Принадлежит **Deviation** (не находке). Решение **живое**, принимается инженером; **не процедурное**, не агрегируется и не выводится автоматически.
- **explanation** — текстовое обоснование. **Присутствует всегда** (импортируется в выходной документ). **Decision не несёт.** Ведётся **вручную**, независимо от Inspection; может *словами* ссылаться на инспекцию («на основании функциональной проверки PPP одобрено»).
- **находки (1..N)** — см. ниже.
- **Inspection (0..N)** — ссылки на исследования, привязка **к находке** (см. §9). Множественны.
- контекст обнаружения (плановая 2-часовая / финальная выборка), дата, приоритет, ответственный, WO, MRB-контекст.
- Система **не проверяет** наличие explanation/Inspection (нет валидации обязательности).

### Находка (рабочий термин)
**Находка = отклонение по одному размеру внутри Deviation.**
- Состав: (Item-локальный размер) + направление + величина, **либо** качественный результат (пин заходит/не заходит).
- **Адресуема** для поиска по размеру.
- **Decision НЕ несёт.**
- Deviation содержит **все** свои находки как единое целое (это одна физически проверенная деталь со всеми этими отклонениями).

### Гранулярность: поиск vs решение
- **Поиск** по (Item + размер) матчит по **находке**, но **единица выдачи — всегда Deviation целиком** (полная картина, все размеры, итоговый decision). Поиск никогда не отдаёт «голую» находку.
- **Решение и целостность** — на уровне **Deviation**. Нельзя расщепить Deviation по размерам — потеряется картина детали.
- Decision строки может быть «любое непропускаемое → reject всего», либо кумулятивным — это **прерогатива инженера**, не логика системы.

### Кросс-связки размеров — НЕ в модели
«AA одобряется, если BB в норме» — **не структура данных**, не часть Deviation/Item, система это **не обрабатывает**. Живёт только как свободный **текст** внутри исследования/explanation.

### Выходной документ אישור חריגה
- Генерируется **только для одобренных** Deviation (decisionDev = одобрено). Для reject не нужен.
- explanation импортируется в этот документ.
- Зафиксировано как **выходной артефакт** Deviation; формат — позже.

## 9. Inspection — намечено (детальный разбор — следующая сессия)

- **Самостоятельная сущность.** Несёт **свой decisionInsp** — **независимый** от decisionDev (никакого наследования; две независимые характеристики двух сущностей).
- **Привязка к находке** (Вариант B), не к Deviation целиком — чтобы работал запрос «все inspections Item XXX по размеру AA».
- **0..N на Deviation** (множественность — следствие множества находок: разные размеры могут требовать разных исследований).
- Inspection **копит информацию**, но **не диктует** decisionDev.

### Логика принятия решения (принцип — ключевой)
- **Решения живые, не процедурные.** Принимаются на основе массива накопленной информации + исследования + контекста причины.
- Почему не процедурно: даже при положительном исследовании по самому размеру инженер смотрит сопутствующее — например **чистоту поверхности**, чтобы понять причину (сломанный инструмент → задиры → reject, хотя числа в норме; либо программная ошибка → одобрение). Это в числах не выражается.
- **Задача базы — дать исчерпывающий объём информации, а не принять решение за инженера.** База — память и поисковый аппарат, не арбитр.
- Пример накопления прецедентов по (XXX, AA): +0.03 → reject; +0.01 → нужна новая inspection → одобрено; +0.005 → inspection не нужна (уже одобряли до +0.01); −0.004 → нужна новая inspection (по отрицательным не проверяли). Это **подача информации** инженеру, не авторешение.

### Две формы-близнецы (целевой паттерн запросов)
- «Все **deviations** Item XXX по размеру AA».
- «Все **inspections** Item XXX по размеру AA».
- Симметрия на уровне размера — ради неё находка адресуема, а inspection привязан к находке.

## 10. WO (рабочий наряд) — отложено

- Сейчас моделируем как **обязательный атрибут** Deviation (по нему достают детали со склада, поднимают рабочую документацию; к нему привязаны NCR и корректирующие действия).
- Valerii склоняется к атрибуту, но опасается, что при расширении функционала упрёмся в необходимость повышения в сущность.
- **Рамка для будущего решения (рекомендация Claude):** атрибут достаточен, пока WO — просто общий идентификатор для группировки. Становится сущностью, когда начинает **владеть своими данными/связями** (MRB-статус, NCR, корректирующие действия, ссылки на документацию). По описанию у WO уже есть «гравитация сущности».
- **Предварительная рекомендация:** на финализации почти наверняка выделим WO в сущность; до тех пор моделировать так, чтобы **повышение из атрибута в сущность было дешёвым** (не размазывать WO-данные по строкам отклонений).
- Финальный вердикт — при полной картине (решение самого Valerii).

## 12. Сводка сущностей (промежуточная, НЕ финал)

| Сущность | Что это | Ключевое |
|---|---|---|
| Item | Производимая деталь/компонент | Центральный узел; локальные характеристики |
| Характеристика (размер) | Атрибут Item | Зависит от Item; ключ (деталь + локальный №); номер локален |
| CharacteristicGroup | Каноническая группа | Общий референс на семейство (connection zone, drill shank) |
| Каноническая характеристика | Слот внутри группы | Якорь группировки; хранит значения/допуски по состояниям |
| State | Стадия (до/после ЭП, закалка) | Меняет номер И значение характеристики |
| Mapping | (деталь, лок. №) → (канон. характеристика, состояние) | Ручной, инкрементальный, необязательный |
| Deviation | Отклонение | Сущность; Item + WO; decisionDev (живой); explanation всегда; находки 1..N; → אישור חריגה при одобрении |
| Находка | Отклонение по размеру внутри Deviation | (Item-размер)+направление+величина / качеств.; адресуема; decision НЕ несёт |
| Inspection | Исследование | Сущность; decisionInsp независим; привязка к находке; 0..N; копит информацию |
| Explanation | Текстовое обоснование | Всегда; в документ אישור חריגה; decision НЕ несёт |
| WO | Рабочий наряд (партия) | Пока атрибут Deviation; кандидат в сущности (отложено) |

> Имена рабочие. Единую диаграмму собираем **после** передачи оставшейся вводной и закрытия открытых вопросов.
