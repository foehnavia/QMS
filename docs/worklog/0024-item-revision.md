## Что сделать

### 1. Схема — ревизия 0.2 → 0.3, одна миграция

Новая таблица `item_revision`:

| Колонка | Тип | Смысл |
|---|---|---|
| `revision_id` | PK | |
| `item_id` | FK → `item.item_id`, `ON DELETE CASCADE`, NOT NULL | владелец |
| `designation` | текст, NOT NULL | обозначение **как выпущено** (`A`, `B`, `A1`, …). Не номер, не парсится |
| `seq` | int, NOT NULL | явный порядок внутри детали: система обязана уметь назвать «предыдущую» |
| `is_current` | bool, NOT NULL | действующая ревизия |

- `UNIQUE (item_id, designation)`, `UNIQUE (item_id, seq)`.
- **Ровно одна действующая на деталь** — частичным уникальным индексом
  `UNIQUE (item_id) WHERE is_current = 1` (SQLite это поддерживает). Циклический FK
  `item.current_revision_id` отвергнут заранее: он ломает вставку первой ревизии.
- Порядок хранится **явно** (`seq`), а не выводится из `designation`: обозначение — строка
  как выпущено, и алфавитный порядок на ней не гарантирован.

Переезд владельца (это и есть суть наряда):

| Таблица | Было | Стало |
|---|---|---|
| `characteristic` | `item_id`, `UNIQUE (item_id, local_number)` | `revision_id`, `UNIQUE (revision_id, local_number)` |
| `item_position_absent` | `(item_id, g_position_id)` | `(revision_id, g_position_id)` |
| `deviation` | `item_id` | `item_id` **остаётся** + `revision_id` NOT NULL FK |

- `mapping` **не трогается**: он висит на `characteristic` и получает ревизию через него.
  Колонки ревизии у маппинга не появляется — это ратификация 3, не экономия.
- `finding` **не трогается**: висит на `characteristic`, ревизию наследует.
- `characteristic.state_depending` (self-FK) остаётся; добавить гард: обе стороны — в одной
  ревизии.
- `deviation.item_id` сохраняется намеренно: он нужен для выдачи «по детали целиком»,
  поверх всех ревизий (`Search.md`), и без него каждый такой запрос шёл бы через join.
  Инвариант: `deviation.revision_id.item_id == deviation.item_id` — доменной проверкой.

Данные (тестовая база расходная, но миграция обязана быть корректной):

- каждой существующей детали завести ревизию `A` (`seq = 1`, `is_current = 1`);
- перецепить на неё все `characteristic` и `item_position_absent` этой детали;
- проставить `deviation.revision_id` = ревизия `A` её детали.

### 2. Домен

- `items.py`: заведение детали создаёт её первую ревизию — **обозначение вводится
  оператором**, молчаливого дефолта нет (ратификация 4). Полнота привязки (наряд `0018`)
  проверяется **в пределах заводимой ревизии**.
- Новая операция **клонирования ревизии**: `clone_revision(item, from_revision, designation)`
  — копирует в новую ревизию все размеры (локальные номера), маппинги (по g-позиции) и
  строки 99; ставит её действующей, прежнюю снимает. Прежняя ревизия и всё, что на неё
  ссылается, **не меняется ничем**.
- `deviations.py`: `revision` — обязательный параметр регистрации; по умолчанию действующая;
  инвариант «отклонение и все его находки в одной ревизии» — доменной проверкой, как гард
  «находка ∈ деталь отклонения» (S2).
- `characteristics.py`: автосоздание не-канонного размера — **внутри ревизии отклонения**.
- `groups.py`: добавление g-позиции в существующую группу требует ответа (маппинг или 99)
  **только от действующих ревизий** деталей группы; прошлые остаются без ответа —
  ратификация 7. Третьего состояния не заводить: «без ответа» — это отсутствие строки.
- `groups.py`: производный признак **«нет деталей в действующей ревизии»** — вычисляемый
  запрос, не колонка, не флаг (ратификация 8).
- `precedents.py`: канонный путь `(cg, g_index)` разрешается через маппинг **той ревизии,
  которой принадлежит находка**. Прямой путь `(item, local#)` ищет по всем ревизиям детали и
  возвращает ревизию каждого совпадения — она нужна выдаче для пометки.

### 3. Интерфейс

- **Форма детали:** поле ревизии при заведении (ввод обязателен); список ревизий детали с
  указанием действующей.
- **«Добавить ревизию»** — форма открывается **уже заполненной** значениями предыдущей
  ревизии: локальные номера, привязки, строки 99. Оператор правит только изменившееся и
  сохраняет. Это ключевое требование пользователя: ревизия с одним сдвинутым допуском и
  ревизия, где переехали все номера, обязаны стоить одного и того же действия.
- **Форма отклонения:** выбор ревизии **до** находок, по умолчанию действующая; перевод на
  предыдущую — отдельным явным действием (детали прежнего выпуска приходят из цеха ещё
  два-три месяца).
- **Смена ревизии в форме ничего не пересчитывает** (ратификация 11): введённые локальные
  номера остаются как введены, меняется только ревизия, против которой они читаются.
  Не перецеплять, не сбрасывать, не спрашивать. Номер, которого в выбранной ревизии нет,
  показывается пометкой **«not in this revision»** — он попадёт под действующее правило
  автосоздания не-канонного размера, и оператор обязан это видеть **до** сохранения.
- **Карточка отклонения и списки прецедентов** — две пометки (`Search.md`):
  - в строке прецедента — «та же деталь, другая ревизия», всегда при расхождении ревизий;
  - на **не-канонном** размере — предупреждающий знак `!`: за его номером не стоит
    g-позиция, совпадение держится на одном номере. У канонного размера пометки нет — он
    разрешается через маппинг своей ревизии и верен сам собой.
  Совпадение через ревизию **не отсеивается никогда** — только помечается.
- **Диалог позиций (код 99)** — в пределах выбранной ревизии.
- Подписи — English, словами канона: `Revision`, `Current revision`, `Add revision`,
  `not in this revision`. Направление — по правилам `CLAUDE.md` §9 (шасси LTR, направление
  на уровне ячейки).

### 4. Тесты

- миграция на чистой БД и на копии тестовой базы: у каждой детали появилась `A`, размеры и
  99 перецеплены, у каждого отклонения проставлена ревизия;
- `UNIQUE (revision_id, local_number)` держит; частичный индекс не даёт двух действующих;
- клон: новая ревизия несёт те же номера, маппинги и 99; **прежняя не изменилась ни в чём**
  (сверка построчно, а не по счётчику);
- регистрация отклонения проставляет действующую ревизию; смена ревизии в форме сохраняет
  введённые номера;
- канонный прецедент через разные ревизии разрешается через маппинг **своей** ревизии
  (тест на пару деталь/ревизия, где номер размера переехал);
- обе пометки появляются там, где положено, и **не появляются**, где нет: канонный размер в
  той же ревизии — без пометок;
- добавление g-позиции в группу не трогает прошлые ревизии;
- дымовой тест точек входа всех затронутых экранов (правило после наряда `0017`).

## Критерии приёмки

1. `alembic upgrade head` проходит на чистой БД и на копии тестовой; `downgrade` не требуется.
2. Вся текущая тестовая база после миграции живёт под ревизией `A`; ни одного отклонения без
   ревизии.
3. Все прежние тесты зелёные + новые по списку выше. Прогон целиком, без `-k`.
4. **Прогон руками** (`CLAUDE.md` §9а): завести деталь с ревизией, зарегистрировать по ней
   отклонение, склонировать ревизию с правкой одного номера, зарегистрировать отклонение по
   новой ревизии, открыть карточку — обе пометки видны, канонный прецедент через ревизии
   найден. Снимки экранов — в отчёт.
5. Печать и подписи — ASCII/English, консоль cp1255 не ломается (`INFRASTRUCTURE` §8).
6. `canon hash HEAD` на приёмке совпадает с записанным в шапке.

## Не входит — объявленное отсутствие (§3б)

Перечислено здесь **заранее и с основанием**, поэтому отсутствием-расхождением не является:

- **Клонирование группы одной кнопкой.** Механика ратифицирована (решение 6), но событие
  редкое; до первой реальной смены допуска у семейства группа-клон заводится руками.
  Схемы не касается.
- **Пометка группы «нет деталей в действующей ревизии»** в интерфейсе. Признак вычисляемый,
  данных достаточно в любой момент; показ — отдельная работа.
- **Ленивая перепривязка переехавших номеров между ревизиями** (решение 9). Создаётся
  вперёд, по факту отклонения; задним числом достраивать нечего, миграции не требует.
- **Подсветка ревизии ~2 месяца после смены дефолтной.** Оформление.
- **Несколько групп характеристик на деталь** (решение 12). Связь `Item↔CG` остаётся
  выводимой (`characteristic → mapping → g_position → cg`) и теперь выводится **по ревизии**;
  материализация — за пределами Этапа 1.
